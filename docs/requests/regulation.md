# Регламент работы с запросами на изменение (requests)

Изменения — решением владельца.

## 1. Что такое запрос

Запрос на изменение — просьба бизнеса (или внутренний запрос) о том, что сделать, добавить или изменить в продукте. Исходный материал: транслированные запросы пользователей + видение бизнеса. Запрос — **сырьё**: субъективный взгляд, как правило без учёта зависимостей, затрат на разработку и поддержку, консистентности с остальным продуктом.

Запрос — это **задача анализа**, а не разработки. Его результат — одно из двух: «не нужен / неактуален» (закрыть) или «достаточно проработан, идём в работу» (запустить research / wayfinder / сформировать эпик).

## 2. Где живут

- Каталог: `docs/requests/` — часть живой документации, но описывает **будущее**, не текущее состояние.
- На запрос — подпапка `<номер>-<краткое-название>/` (без ведущих нулей: `110-название`, `7-название`).
- Основной файл: `request.md` — по шаблону `docs/requests/template.md`.
- В подпапке: артефакты нашего исследования, прототипы (как правило текстовые, изредка мелкие бинарники).
- Исходные данные бизнеса — в задачах трекера задач проекта (в топ-проекте — КИРА; инструменты — [плейбук окружения](../howto/project-environment/playbook.md)), сюда не копируются. Большие бинарники — только в трекере.
- Закрытые запросы: `docs/requests/archive/<номер>-<название>/` — папка переезжает целиком, номер не меняется.
- Каталог исключается из обычного поиска агентов: читать и цитировать — только по явной задаче (команда владельца, работа над конкретным запросом).

## 3. Именование

- **Номер** — следующий свободный (по максимальному в каталоге и архиве + 1). Никогда не меняется. Это идентификатор запроса.
- **Краткое название** — 20–30 символов, формулирует агент по описанию, владелец/автор правит. Входит только в имя папки. В map.md — полное название запроса (раздел 5).
- **Полное название** — название как в заголовке `request.md` (и как дало бизнес/трекер). Встречается в map.md и в заголовках.
- **Номер приоритета** — позиция запроса в списке map.md. Внешняя по отношению к запросу, в файл запроса не входит. Меняется перемещениями.

## 4. Создание запроса

Кто: владелец, аналитик (через владельца) или агент по поручению. Источник: речь/письмо бизнеса, задача трекера, внутренний запрос.

Процедура:
1. Получить исходный текст (без пересказа).
2. Выделить номер, сформулировать краткое название.
3. Создать подпапку, заполнить `request.md` по шаблону: Зачем, Бизнес-цель (первичная, краткая), Оригинал, Трекер (если есть — ключи, иначе «— нет —»), Status `ANALYZING (дата)`, первая запись в Журнале (создан, источник).
4. Добавить строку в `map.md` (позиция — по указанию, иначе в конец списка), обновить шапку map.md (дата, кто).

## 5. Карта (map.md)

Формат:

```
# Requests — карта приоритетов

Обновлено: YYYY-MM-DD, <кто: бизнес / разработка>

1. 110 — Полное название запроса — TRK-1, TRK-2 — ANALYZING
2. 10 — Полное название другого запроса — — PENDING (ждём: бизнес)
3. 7 — Полное название третьего запроса — — READY
```

- Список нумерованный по приоритету: позиция — номер запроса — **полное название** (как в заголовке `request.md`; имя папки — это краткое название, в карте оно не используется) — ключи задач трекера (или «—») — состояние.
- Берём в работу преимущественно с головы списка: чем выше, тем больше шансов попасть в разработку.
- В списке — только актуальные запросы (ANALYZING / PENDING / READY). Закрытых в списке нет — они в архиве.
- Шапка: дата последнего изменения и кто менял (бизнес — если перестановка по списку от бизнеса; разработка — если по нашей инициативе).

## 6. Приоритизация (перемещение)

- **По бизнесу**: владелец передаёт список приоритетов от бизнеса (формат — любой: текст, файл, таблица). Агент переставляет строки map.md: «передвинь запрос N на позицию M» — строка берётся с текущей позиции, ставится на M, все остальные сдвигаются. Номера запросов не меняются.
- **По разработке**: перемещение по оценке развития проекта (зависимости, стоимость, синергия).
- Никаких согласований: приоритизация — вне нашего процесса, ею управляют бизнес и мы самостоятельно. Мы **только фиксируем новый приоритет**: строки map.md, шапка (дата, кто), и — при перемещении по инициативе проекта — строка в Журнале затронутого запроса (дата, позиция A → B).
- Любой запрос можно переместить в любой момент, включая PENDING и READY.

## 7. Состояния

- `ANALYZING (дата)` — запрос зафиксирован, над ним работают.
- `PENDING (дата, ждём: <кто, что>)` — анализ остановлен на ответе/событии (бизнес, владелец, внешний сервис). Пока запрос в PENDING, приоритизация и пересмотр бизнес-цели всё равно возможны.
- `READY (дата)` — всё проработано, готовы пустить в работу, но ещё не пустили. Дальше запрос уходит в работу (`CLOSED (дата, ушёл в работу)`) либо возвращается в `ANALYZING`, если при запуске что-то переоткрывается.
- `CLOSED (дата, <причина>)` — причины: `не нужен`, `неактуален`, `ушёл в работу`.

Смена состояния: правка строки `**Status**` + запись в Журнале (дата, отчего, на что). После CLOSED: последняя запись журнала — причина; папка переезжает в `archive/`; строка убирается из map.md.

Состояниями управляет **продукт-менеджер** (собирает и закрывает запросы): он закрывает запрос, когда сочтёт нужным, и отправляет его в работу — в том числе в обход нашего процесса, без нашего анализа и раньше, чем мы закончили бы. В этом случае в Журнале фиксируем строку «ушёл в работу (внешнее решение, вне процесса проекта)» + ссылка на наследника, если она известна. Процессы работы с запросами и с разработкой не связываются: разные люди, разные ритмы.

## 8. Связь с трекером задач

- У запроса 0..N связанных задач трекера. Внутренний запрос — без задач трекера («— нет —»).
- В секции «Трекер» на каждую задачу строка: `КЛЮЧ — название — краткий пересказ — дата обновления пересказа`.
- Полную синхронизацию описаний **не делаем**: трекер меняется, там комментарии. Пересказ обновляем по событию — когда возвращаемся к запросу (новые комментарии, сменилось описание): подтягиваем суть, обновляем дату.
- Бизнес-цель в запросе — наша формулировка: уточняется и корректируется по мере анализа (Журнал), она же — основа для разговора с бизнесом.
- Файлы и вложения, связанные с запросом, — в задаче трекера; в запросе — ссылка на задачу.

## 9. Анализ (ведение запроса)

- Ведётся в Журнале `request.md` (append-only): вопросы, зависимости, оценка затрат, решения, смена состояний, перемещения. Слова стейкхолдеров — побайтово.
- Открытые вопросы — в секции «Открытые вопросы»: вопрос — кому задан — дата. Получен ответ — вопрос снимается, ответ фиксируется в Журнале.
- Если ждём ответ кого-то — состояние PENDING.
- Артефакты анализа (схемы, расчёты, прототипы) — в подпапке запроса, ссылки из Журнала/Links.

## 10. Итог анализа

Два исхода:
1. **Не нужен / неактуален** — `CLOSED (дата, не нужен|неактуален)`, в архив. Развёрнутая причина — в Журнале.
2. **Ушёл в работу** — запрос стал отправной точкой: запущен research / wayfinder (новый issue в трекере проекта), сформирован эпик или работа запущена в обход нашего процесса. В Журнале — ссылка на наследника, если известна. `CLOSED (дата, ушёл в работу)`, в архив. Дальнейшая жизнь — в наследнике, request больше не ведётся.

Критерий «достаточно проработан, чтобы идти в работу» регламент **не ограничивает**: решение о переходе в работу — на усмотрение продукт-менеджера и команды.

## 11. Версии и волны

- v1.0 — этот регламент + первые 10–20 запросов.
- Последующие запросы — отдельными волнами; процесс тот же, новый.
- Изменения в регламенте — решением владельца, фиксируются (дата, суть) и переносятся в doc в docs/.
