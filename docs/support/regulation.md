# Регламент работы с кейсами поддержки (support)

Изменения — решением владельца.

## 1. Что такое кейс

Кейс — генерализованный тип инцидента поддержки: симптом (что видит
пользователь или поддержка) + сценарий диагностики.

Главное достояние кейса — **сценарий**: последовательность
проверок, по которой по id заявки быстро находят причину — без
повторного исследования кода для каждого нового обращения.

Кейс создаётся **словом владельца**. Агент предлагает — и в
предложении обязан (а) выделить именно возможную повторяемость
сценария: почему этот тип инцидента будет повторяться и по какому
признаку его узнать, и (б) кратко описать сам сценарий (цепочка
проверок). Общее «давай создадим кейс?» — не предложение. Порога по
числу инцидентов нет: один инцидент с описанным сценарием
достаточен (прецедент — кейс 01).

Цель каталога — накапливать инциденты так же, как запросы на
изменение накапливают запросы бизнеса: новый инцидент известного
типа — запускаем сценарий по кейсу и фиксируем результат; новый тип
— агент предлагает, владелец решает.

## 2. Где живут

- Каталог: `docs/support/`.
- На кейс — подпапка `<номер>-<краткое-название>/` (без ведущих
  нулей: `1-название`, `10-название`).
- Основной файл: `case.md` — по шаблону `docs/support/template.md`.
  В подпапке — `case.md` и, если нужны, скрипты и другие артефакты,
  необходимые для разбора ошибки/задачи по кейсу.
- Рабочие файлы при разборе конкретного инцидента (выдержки
  логов, трейсы, дампы) в сценарий не пишутся и не обязаны жить в
  кейсе: на время работы они сохраняются в папку временных файлов
  проекта (`.scratch/<проект>/work/<название>/`). Перепроверки «по
  id записи» регламентом не предусматриваются.
- Факты об инцидентах проверяются средствами окружения проекта —
  поиск по логам, база данных заявок, движок задач, трекер задач
  ([плейбук окружения](../howto/project-environment/playbook.md));
  в кейсе фиксируем проверенные факты и ссылки на источники.
- Закрытые кейсы: `docs/support/archive/<номер>-<название>/` —
  папка переезжает целиком, номер не меняется.
- В отличие от `docs/requests/`, каталог **НЕ исключается из
  поиска**: он — точка входа в диагностику новых инцидентов. Перед
  разбором нового обращения в поддержку смотреть `map.md`.

## 3. Именование

- **Номер** — следующий свободный (по максимальному в каталоге и
  архиве + 1). Никогда не меняется.
- **Краткое название** — 20–30 символов, формулирует агент,
  владелец правит. Входит только в имя папки.
- **Полное название** — как в заголовке `case.md`. Встречается в
  map.md и в заголовках.

## 4. Создание кейса

Создаёт **владелец словом** (сам создаёт или поручает агенту).
Агент до предложения — по порядку: смотрит живую документацию и
существующие кейсы; среди них может быть полностью подходящий
(сценарий выполняется как есть) или частичный (кейс как подпроцесс
анализа / переиспользуемая часть шагов) — это и есть анализ,
который агент выполняет до того, как предложить кейс.

Процедура создания:
1. Зафиксировать симптом: исходный текст первого инцидента —
   побайтово, без пересказа.
2. Создать подпапку, заполнить `case.md` по шаблону: Симптом,
   Быстрая диагностика (сценарий), Корневая причина (факт либо
   «не найдена»), Первый инцидент, первая запись Журнала.
3. Сценарий написать исполняемым: каждый шаг — что проверяем, чем
   (инструмент), какой ожидаемый результат, и куда идти, если
   результат другой. Формат — свободные нумерованные шаги (как в
   кейсе 01), жёсткой таблицы нет. Отдельной финальной ветки
   «не наш тип» в сценарии нет: «не наш тип» — это развилка внутри
   шага, как любой другой «куда идти, если результат другой».
   Под каждым шагом сценария — кодовые ссылки, обязательны: откуда
   взяты искомые данные (строки лога, имена актёров/классов/джобов,
   статусы). Формат ссылки: `код: путь-к-файлу → класс → строка
   побайтово (в кавычках)`; номер строки кода в ссылку НЕ входит
   (номера плывут при правках кода — ссылка означает «найди эту
   строку», номер не нужен).
4. Состояние по шапке: кейс создан уже со сценарием — `READY`;
   зафиксирован без сценария (файл создан, чтобы проработать и
   зафиксировать) — `ANALYZING`.
5. Добавить строку в `map.md`, обновить шапку.

Кодовые ссылки — проверочный список, а не памятка: прогон сценария
начинается с обязательной проверки ссылок с кодом (не рекомендация,
стадия) — исполнитель ищет каждую строку в коде, сверяет
существование классов/актёров. Нашёл всё — кейс валиден, идём по
сценарию. Не нашёл — не гадать и не форсировать: открыть файл/класс,
установить, куда переехала строка или что поменялось; дальше по
регламенту (устаревший кейс — §7, по ситуации / по слову владельца).

После прогона сценария по живому инциденту — **анализ анализа**
(это не шаг сценария): тянет ли ситуация (а) на новый кейс
(агент предлагает по правилу выше), (б) на изменение/дополнение
старого (по §7), (в) не понятно / слишком частный анализ проблемы —
кейс не создаём. Если кейс не создан, фиксировать результат
анализа негде и не надо.

## 5. Карта (map.md)

Формат:

```
# Кейсы поддержки — карта

Обновлено: YYYY-MM-DD

1. 1 — Полное название кейса — TRK-80 — READY
2. 2 — Полное название другого кейса — — ANALYZING
```

- Строка: номер — **полное название** (как в заголовке `case.md`) —
  ключи задач трекера (или «—») — состояние.
- В списке — только открытые кейсы (ANALYZING / READY). Закрытые —
  в архиве.
- Шапка: дата последнего изменения.

## 6. Состояния

- `ANALYZING (дата)` — кейс зафиксирован, сценария нет (файл создан
  для проработки).
- `READY (дата)` — исполняемый сценарий готов; рабочее состояние,
  кейс живёт в map.md. Созданный по слову владельца уже со
  сценарием кейс — READY сразу.
- `CLOSED (дата, <причина>)` — причина — свободная,
  детерминированного списка нет (например: тип инцидента не
  возникает после фикса, больше не возникает).

Смена состояния: **владелец, либо агент — только по слову
владельца**. Правка строки `**Status**` + запись в Журнале (дата,
отчего, на что).

Правил переходов нет: состояние может меняться из любого в любое.

После CLOSED: папка переезжает в `archive/`, строка убирается из
map.md.

## 7. Журнал кейса

- Журнал `case.md` — append-only, свежие записи внизу. Кейса нет —
  фиксировать негде: журнал существует только внутри файлового
  кейса.
- Журнал ведёт **только о внесении изменений в этот кейс**:
  создание, правки сценария, смены состояний. Записей по каждому
  инциденту, по которому прогоняли сценарий, не ведётся.
- Живые инциденты — как правило немного разные. Сценарий, который
  разошёлся, — **по ситуации**: может и чинят, скорее всего
  дополняют знаниями и возможной вариативностью. Всё — только с
  согласием владельца, словом; правка фиксируется в Журнале.
- Слова стейкхолдеров (пользователь, владелец) — побайтово, в
  цитатах.

## 8. Связь с трекером задач и другими каталогами

- Кейс может породить задачу в трекере задач проекта (расследование,
  фикс), запрос на изменение или эпик: трекер проекта — КИРА,
  инструменты — [плейбук окружения](../howto/project-environment/playbook.md);
  ключи связанных задач — в секции «Links» `case.md`, без пересказов;
  данные по задачам трекера в кейсе не копятся.
- Каталог не связывается с процессом разработки: разные люди,
  разные ритмы.
- Запросы (`docs/requests/`) — зафиксированное будущее; кейсы
  (`docs/support/`) — прошлое + диагностика. Если кейс показывает
  не дефект, а продуктовый недостаток — создаём запрос на
  изменение, в кейсе — ссылка.

## Роль в диагностике

Отдельной роли «поддержка» в регламенте нет: при разборе
ошибок/проблем поддержку представляют **владелец и агент**.
Порядок: задача «разобраться с чем-то на проде/тестинге/
стейджинге» сообщается агенту → агент смотрит живую документацию и
существующие кейсы → среди них ищется полный или частичный
совпавший кейс → агент выполняет анализ (сценарий как есть или
его часть как подпроцесс).
