# Спецификация компонента: metrics-subsystem

## Ответственность | Responsibility
Собирает события (отметки) операций оркестратора задач, агрегирует их в ряды данных в памяти процесса и предоставляет ряды веб-консоли. Основной компонент домена [metrics](../domain.md).

## Интерфейсы и Контракты | Interfaces and Contracts
- **Metric.mark(dataset, value)**: событие → увеличение контрольной точки ключа (атомарная CAS-операция). Первая отметка создаёт ключ в метрике.
- **Metric.dump(listener)**: без входа → для каждого датасета вызов `listener.handle(metricName, datasetName, count, mean, time)`. Вызывается планировочным потоком раз в период дампинга; обходит все ключи, включая неактивные (count = 0, mean = NaN).
- **GET /console/metrics/data**: параметры `metric` (имя метрики), `type` (dataType: rate/mean/size), `period`, `scope`, `dataset` (список через запятую; пустой — пустой ответ), `zeroes` (default true), `smooth` (default −1) → датасеты с рядами за запрошенное окно (точки `[time, value]`, `[null, null]` — маркер прогона пропущенных значений);
- **GET /console/metrics/options** → доступные метрики и опции консоли.

## Логика и Алгоритмы | Logic and Algorithms

Конвейер сбора и хранения:

1. **Отметки.** Сервисный модуль при каждой операции актёра вызывает `Metric.mark` соответствующей метрики с именем датасета (FQN+версия актёра или джоба). Метрика хранит по контрольной точке на ключ (счётчик и сумма). Отметка двойная: по датасету актёра и в агрегате (датасет = имя метрики); отметки условны: успешный poll отмечается только если poll вернул задачу, ошибка решения — только при ошибке в решении.
2. **Дампинг.** При первом экземплярировании `MetricsFactory` расписывает задачу на метрику: раз в период дампинга — `Metric.dump` обходит все датасеты и передаёт их состояние (сбрасывается через `getAndSet`) обработчику.
3. **Методический обработчик** (`MetricsDataHandler`). Два хранилища: «последний час» — кольцо из 3600/бин-секунд бин (по умолчанию 360 бин × 10 с) и «последний день» — из 86400/бин-секунд бин (по умолчанию 720 бин × 2 мин). Бин адресован абсолютным временем данных (не временем жизни процесса). `handle()`: дамп со значением count = 0 ничего не пишет (строка и точка не создаются); иначе при первом использовании создаёт строку (счётчик берётся полным с контрольной точки) и пишет бин текущего времени в часовое и суточное кольцо: в бине count += , среднее — взвешенное усреднение по count; накопление — только в пределах одного абсолютного интервала бина, при переиспользовании слота (полный оборот кольца) данные прежнего оборота сбрасываются. Суточный бин пишется каждым тиком напрямую (без «минутной границы»). При создании строки проверяется лимит строк хранилища: при превышении удаляются строки с самым старым временем последней активности среди невидимых (часовое хранилище — неактивны дольше 1 ч, суточное — дольше 24 ч); видимые не затрагиваются, кандидатов нет — вытеснение пропущено со счётчиком.
4. **Периодические метрики** (`NumberDataHandler`, `PeriodicMetric`). Выборочные значения (размер очереди, память) пишутся в единственное кольцо из 86400/бин-секунд бин (по умолчанию 1440 бин × 1 мин) — независимо от интервала выборки (queue-size — 5 с, memory — 10 с). Бин хранит последнее значение (last-write-wins); «последнее значение» — свежайший заполненный бин (null, если данных нет). Лимит строк, TTL и статус-лог — как у методических хранилищ (окно 24 ч).
5. **Память: TTL и статус-лог** (задачи хранилищ, один планировщик на обработчик, период — свойство, по умолчанию 10 мин): удаляются строки, неактивные дольше TTL (по умолчанию 24 ч) — методический ключ из обоих хранилищ разом; ключи-счётчики не удаляются. INFO-строка: число строк по хранилищам, вытеснено/удалено/вытеснение-пропущено с предыдущей строки, heap JVM (used/committed/max); счётчики обнуляются после записи.
6. **Консоль** (`MetricsDataProvider`): собирает ответ из хранилищ, окно выбирается по запрошенному периоду. Методические метрики отдают rate/mean за час/сутки — только полные бины (недополненный бин в отдаче точек отсутствует); «всего за последний час/сутки» — сумма всего кольца, включая недополненный бин (потребляется карточкой очереди и статистикой актёров; допуск — один бин: 10 с / 2 мин); числовые метрики — только size (шаг подмножества — секунды бина, не период выборки); ошибка провайдера → HTTP 500.

### Набор метрик
Перечень имён метрик задаёт перечисление `MetricName` (13 значений): методические счётчики операций (`startProcess`, `poll`, `successfulPoll`, `release`, `executionTime`, `errorDecision`, `enqueue`), периодические выборки (`queueSize`, `memory`, `operationExecutorSize`, `garbageCollectorQueueSize`) и метод-метрики `storage`/`recovery`. Методические метрики пишет `MetricsDataHandler`, выборочные значения — `NumberDataHandler`. Действительно активны в боевой конфигурации: периодические `queueSize` + `memory`; бины `operationExecutorSize`/`garbageCollectorQueueSize` закомментированы, классы `storage`/`recovery` не подключены к spring (мёртвый код).

### Поведение памяти (текущее состояние)
- Строка создаётся при первом использовании и может удаляться: TTL (по умолчанию 24 ч) и вытеснение при превышении лимита (по умолчанию 1500 строк на хранилище) — только самая старая невидимая строка; следующая отметка воссоздаёт строку с полным счётчиком с контрольной точки.
- Кольца заполняются по времени данных, независимо от интенсивности нагрузки: часовое кольцо охватывает последние 3600 с, суточное и периодические — последние 86400 с.
- Удерживаемая память пропорциональна (числу строк) × (размерам колец): каждая строка методических хранилищ несёт два массива бин (count и среднее), числовая строка — один; точка — объект (число + время бина).
- Набор ключей определяется актёрами/джобами, побывавшими на сервере хотя бы один раз: новый ключ появляется только при первой встрече нового FQN+версии; набор ключей-счётчиков монотонно растёт, набор хранимых строк ограничен TTL и лимитом.
- Статус-строка (INFO, период по умолчанию 10 мин): число строк по хранилищам, вытеснено/удалено/вытеснение-пропущено с предыдущей строки, heap JVM (used/committed/max) — наблюдение за памятью без дампов.

## Конфигурация
- `metric.data.method.period-in-seconds` (1) — период дампинга методических метрик;
- `metric.data.queue-size.period-in-seconds` (5) — период выборки `queueSize`;
- `metric.data.memory.period-in-seconds` (10) — период выборки `memory`;
- `metric.data.method.hour-bin-seconds` (10) — длина бина часового хранилища;
- `metric.data.method.day-bin-seconds` (120) — длина бина суточного хранилища;
- `metric.data.periodic.bin-seconds` (60) — длина бина периодических метрик;
- `metric.data.store.max-rows` (1500) — лимит строк на хранилище;
- `metric.data.store.inactive-ttl-seconds` (86400) — TTL неактивных строк;
- `metric.data.status-log-period-seconds` (600) — период статус-строки (к нему привязана TTL-уборка);
- размеры колец выводятся из длины бина: час — 3600/бин секунд, сутки и периодические — 86400/бин секунд (окно 24 часа).
- Валидация на старте: длины бин положительны и делят окно (час — 3600, сутки/периодические — 86400), лимит/TTL/период статус-лога положительны; иначе — отказ старта контекста с сообщением, называющим свойство.
- Spring-связывание: бин `metricsDataHandler` (`taskurotta/src/main/resources/spring/backend/hazelcast.xml`), фабрика метрик (`taskurotta/src/main/resources/spring/statistics/task-server.xml`), связывание консоли (`taskurotta/src/main/resources/spring/rest/console.xml`).

## Зависимости | Dependencies
- $\rightarrow$ сервисный модуль — источники вызовов `mark` (операции жизненного цикла задач и процессов);
- $\rightarrow$ Hazelcast — размеры очередей для периодических метрик;
- $\rightarrow$ модуль dropwizard — REST API консоли.
